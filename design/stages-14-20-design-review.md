# Stage 14〜20 設計確定用レビュー

作成: 2026-10-23。対象は [第1候補](prototypes/stages-13-20-v1/README.md)（地形・CLI検証済み）。ユーザーが採用・手直しを判断するための資料で、製品への採用や実機合格の記録ではない。Stage 13 は 2026-10-12 の本人試遊でクリアを確認し、設計は確定扱いとした（[試遊記録](prototypes/stages-13-20-v1/PLAYTEST.md)）。

## 読み方

- 地図は各候補の seed 0。`@` プレイヤー、`S`／`0`／`1` 石（番号は石0・石1）、`*` 岩・地面、`G` ゴール。行番号は下から数える。地図の空行（何もない上空）は省略した。
- コードは製品の書き方に合わせた想定解。Keystone は `loop N … end`／`while 条件 … end`／`if 条件 … end`、方向は `up` `down` `left` `right`。Rhai は `move("right")` `place("down")` `dig("right")` `sleep(秒)` `is_touched()` `is_empty("方向")`。
- 「CLI」は `tools/stage_sim` で同じ操作を1手ずつ実行し、100 seed すべてで到達したことを指す。製品のゲーム内で、このコードを実行した確認はまだない。
- 石の種類で使える命令: Type1 は move・sleep、Type2 は move・is_touched・is_empty、Type3 は Type1・Type2 の命令と dig、Type4 は move・is_touched・is_empty・place。

## Stage 14: 石を動かしながら橋を作る

```text
  7 #.@..........................#
  6 #***.........................#
  5 #.......S....................#
  4 #*******.......*****.........#
  3 #*******.......**.****.......#
  2 #*******.......**...****...*G#
  1 #****************.....******G#
```

左の高台（x1〜7）と右の岩（x15〜）の間に幅7マスの穴。石は穴の左端の上にいる。足元に置いて右へ1歩、を7回で y4 に橋を架け、最後に石を上へどかしてプレイヤーが渡る。

```text
loop 7
    place down
    move right
end
move up
```

```rhai
for _ in 0..7 {
    place("down");
    move("right");
}
move("up");
```

- CLI: 100/100 到達。上限6では資源不足になる。地形の変化は出口側だけ。
- 判断してほしいこと: 7マスの長さ（反復の練習として妥当か、単調か）。最後に石を上へどかす発想が自然に出るか。

## Stage 17: 2つの石を乗り継ぐ（Type1・待機）

```text
  7 #........................*...#
  6 #......@.....................#
  5 #......0.........1.........*G#
  4 #*******.....*****.....*****G#
  3 #*******.....*****.....**..*G#
  2 #*******.....*****.....**..*G#
  1 #************************..*G#
```

プレイヤーは最初から石0の上にいる。石0が右へ6マス運び、中間の足場（x13〜17）へ降ろす。プレイヤーは歩いて石1（x17）へ跳び乗り、石1が対岸（x23〜）へ運ぶ。Type1 は接触を判定できないので、石1は sleep でプレイヤーの到着を待つ。

石0:

```text
loop 6
    move right
end
```

石1:

```text
sleep 12.0
loop 6
    move right
end
```

```rhai
// 石0
for _ in 0..6 {
    move("right");
}

// 石1
sleep(12.0);
for _ in 0..6 {
    move("right");
}
```

- CLI: 100/100 到達。ただし CLI は1手ずつ順に動かしたもので、2石が同時に動く製品での時間の余裕は未確認。12秒は旧候補の値で、根拠のある値ではない。
- 中間の足場があるので、石1に乗り遅れても落ちずに済む。その場合は、リセットして秒数を直すことになる。
- 判断してほしいこと: 待機秒数を合わせる遊びを、本編に入れてよいか（設計方針は「厳密な秒数同期を初見の必須条件にしない」）。余裕を大きく取れば、方針と矛盾しない見込み。

## Stage 18: 触れた石が動く乗り継ぎ（Type2・接触待ち）

```text
 12 #....................*.*.....#
 10 #............0...............#
  9 #.......*****......*********G#
  8 #.........................**G#
  7 #..........................*G#
  6 #......@...................*G#
  5 #......1...................*G#
  4 #*******...................*G#
  3 #..........................*G#
  2 #..........................*G#
  1 #********************......*G#
```

プレイヤーは最初から下側の石1の上にいる。石1が上へ4マス運び、プレイヤーは上の足場（x8〜12）を歩いて上側の石0（x13）へ跳び乗る。触れられた石0が右へ6マス運び、対岸（x19〜）へ渡す。番号は上から順に付くため、**上側が石0、下側が石1**。

Rhai（接触するまでループで待つ。製品の Rhai 実行器はループの途中で処理を区切るので、待ち続けても固まらない想定）:

```rhai
// 石0（上側）
loop {
    if is_touched() {
        for _ in 0..6 {
            move("right");
        }
        break;
    }
}

// 石1（下側）
loop {
    if is_touched() {
        for _ in 0..4 {
            move("up");
        }
        break;
    }
}
```

Keystone の候補:

```text
while not is_touched()
    wait = 0
end
loop 6
    move right
end
```

- **要確認**: Keystone の `is_touched()` は「今触れているか」を返すだけで、待つ命令はない。`while` の中身には文が1つ以上必要なため、何もしない代入（`wait = 0`）で待つ形にした。この書き方で、ゲームが固まらずに毎フレーム判定し直すかは確認していない。Type2 は sleep も使えない。段階1の確認（Astra）で調べる。
- 書けなかった場合の選択肢: Keystone に待つ書き方を足す（言語側の変更）か、18 の設計を変える。
- CLI: 100/100 到達（逐次の手動操作）。

## Stage 19: 2区間を掘って通路を空ける（Type3）

```text
  7 #......................*.*...#
  6 #**********************......#
  5 #....@...0**......1**......*G#
  4 #**********.********.*******G#
  3 #**********************....*G#
  2 #**********************....*G#
  1 #**********************....*G#
```

通路（y5）に岩が2か所あり、それぞれの左に石がいる。各石が右を2回掘って進み、最後に足元の穴（x11、x20）へ下がって、通路をふさがないようにする。

石0・石1（同じコード）:

```text
loop 2
    dig right
    move right
end
move down
```

```rhai
for _ in 0..2 {
    dig("right");
    move("right");
}
move("down");
```

- CLI: 100/100 到達。片方の石を省くと全件失敗。
- **設計方針との食い違い**: [最終提案](stage-design-final-proposal.md) は 19 を「一方が通路を開き、もう一方が次の区間を掘り進む」「2石に同じ掘削をさせるだけにしない」としている。今の候補は、2石がまったく同じコードになっている。
- 判断してほしいこと（次のどれか）:
  1. このまま採用する。「同じコードを2つの石に書く」こと自体を、複数石の確認として受け入れる。
  2. 片方の役割を変える。たとえば石1は下へ掘って縦穴を開け、プレイヤーが降りる経路にする。地形を作り直し、CLI 検証もやり直す。
  3. 掘る量や方向を2石で変えて、地形を読む要素を足す。小さな手直しで済む。
