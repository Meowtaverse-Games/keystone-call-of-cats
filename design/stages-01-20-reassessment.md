# 20ステージの再設計 — mainの遊びを引き継ぐ構造案

更新: 2026-09-28。比較対象: `origin/main` = `43a8df9`、統合ブランチ = `5196551`。

## 今回の方針変更

ユーザーはStage 8検証を通して、それまでのゲームらしい面白さが失われていると判断した。Stage 8の個別抽出を次の作業とする従来handoffを変更し、既存ステージを極力生かした20面の全体構造を確認した後、Stage 1から順に設計する。

ここで確定しているのは進め方の変更である。以下の新しい面構成、特に13〜20の内容と石数は確認用の提案であり、採用済みではない。地形・製品コード・ロケールはこの整理では変更しない。

統合案の目的は固定20面の再現可能な解法・進行・検証を揃えることだった。しかし、開始時から石に乗せる、水平経路へ寄せる、複数石を減らす、といった変更で、石に辿り着くまでの操作や地形を読む余地まで削っていた。固定配置そのものと、地形の単純化は分けて判断する必要がある。

## 石の種類と実装上の境界

| 石 | 使える命令・判定 | 遊びの役割 |
| --- | --- | --- |
| Type1 | move / sleep | 移動する足場、出発待ち、乗り継ぎ |
| Type2 | move / is_touched / is_empty | プレイヤーとの接触で動く足場。sleepは使えない |
| Type3 | move / sleep / is_touched / is_empty / dig | 岩を掘って道を開き、動く足場にもなる |
| Type4 | move / is_touched / is_empty / place | 足場を置いて道を作る。dig・sleepは使えない |

loopやifは石固有の命令ではなく言語構文。RhaiとKeystoneの反復・待機の違いを同一視しない。接触待ちの現行Stage 8試作はRhaiの無限loopを使う。

現行RONはステージにstone_typeを1つ指定し、その面の全石が同じ種類になる。Type3とType4を同じ面で混在させる案は追加実装が必要なので、今回の構造案には含めない。Type3のdig上限は石ごと、Type4のplace上限はステージ共有である。

17〜20をType1→Type2→Type3→Type4の応用にするのは今回の提案。現行候補17・18のType3は採掘を想定解で使っていないため、能力と課題の関係を分かりやすくする。複数石の初登場を17まで遅らせず、11と16で既に体験する構造になる。

## 設計時に守ること

- mainの岩塊・高低差・足場・石の位置関係を最初に読む。旧候補からの単純な差し戻しだけで完成とはしない。
- 「入口→石へ到達→石で経路を変える／乗る→降りる→出口」の遊びを先に描き、必要な命令を対応させる。
- 導入面では簡単さを保つが、教える命令以外の移動を一律に削らない。
- 4面ずつの章区切りに地形や石数を合わせない。1〜6基本石、7〜8接触石、9〜12採掘石、13〜16配置石、17〜20応用を確認用の大枠とする。
- 固定配置かchunk生成かは既存の遊びと再現性を見て面ごとに判断する。この構造案では一括固定化を前提にしない。生成を残す場合はseedを記録して確認する。
- 地形と一致しない説明をそのまま使わない。面を採用する際に3言語の導入・命令説明・ヒントを合わせる。
- CLI成立、製品物理の成立、人の感じる面白さは別々に記録する。

## Stage 1からの進め方

1. この20面の石種・主題の構造をユーザーと確認する。
2. mainのStage 1の開始・中間・ゴールchunkを図にし、下降、段差、着地点、出口までの動線と石の役割を確認する。
3. 残す部分と改善したい部分を明示したStage 1案を作る。操作する石・コードは必須にしない。固定化の要否もここで判断する。
4. 実機で道の読みやすさ、ジャンプ、落下後の再試行、クリア、リセット、面白さを確認する。
5. 合格したStage 1だけを個別の変更として採用し、Stage 2へ進む。

Stage 8の先行抽出と旧20面候補の一括採用は進めない。Stage 18の旧失敗計画は既知課題として保持し、新しい案の検証結果と混ぜない。
